# Proposal: архитектура field-семейства (общий `Field` + отдельные компоненты)

**Статус:** proposal (обсуждение, до перестройки ничего не трогаем)
**Дата:** 2026-07-21
**Автор:** дизайн-система
**Триггер:** при добавлении каретки/Editing в Search пришлось **вручную копировать** решения из Input v2 — сигнал, что общей основы нет и компоненты дрейфуют.

---

## 1. Проблема

Поля ввода (Input, Search, Textarea) визуально идентичны по «обвязке» (контейнер, границы, состояния, размеры, label, supporting), но реализованы как **независимые копии**. Любая правка chrome (например, «добавить фокус-обводку заливным») переносится руками в каждый компонент → дрейф и рассинхрон.

Отдельная проблема — **нет Select / Combobox / Dropdown** вообще, хотя это базовые члены того же семейства.

---

## 2. Инвентаризация (факт на 2026-07-21)

| Компонент | Set | Вариантов | Оси | State |
|---|---|---|---|---|
| **Input v2** | `6316:335` | 42 | Type × Size × State | Default, Focused, **Editing**, Filled, **Error**, Disabled, **ReadOnly** (7) |
| **Input v2 Stacked** | `6346:304` | 14 | Type × State | как Input |
| **Search v2** | `6447:268` | 30 | Type × Size × State | Default, Focused, **Editing**, Filled, Disabled (5) |
| **Textarea** | page `9727:10` | 12 | Type × State (без Size) | Default, Focused, Filled, **Error**, Disabled, **ReadOnly** (6) |
| **Select / Dropdown** | — | — | — | **отсутствует** |
| **Combobox / Autocomplete** | — | — | — | **отсутствует** |
| **Date / Time picker, Stepper** | — | — | — | отсутствует |

**Chrome (Field):** у Input и Search **идентичен** — `radius/control/control-lg`, padH `spacing/3` (md), height `control-height/md`, border `Border/Default` 1px, HORIZONTAL. Textarea — тот же язык, но multiline (без Size, высота растёт).

### Выявленные расхождения (drift)

1. **State-модель НЕ едина** (главное):
   - Input: 7 состояний (полный набор).
   - Search: **нет `Error` и `ReadOnly`**.
   - Textarea: **нет `Editing`**.
2. **Нейминг булевых расходится:** Input — `Left Icon#`, Search — `Leading Icon#` (один и тот же концепт, разные имена).
3. **Size:** Input/Search — lg/md/sm; Textarea — без Size (осознанно, multiline).

---

## 3. Рекомендация

**Не** один мега-компонент с осью `Type=input|select|search`. **Не** независимые копии. А **композиция**:

### 3.1 Общий building-block `Field` (новое)

Единый примитив-обвязка, который композируют все поля:

```
.=Field (building block)
├── контейнер: layoutMode, radius (radius/control/control-lg), padding (spacing/3…4 по Size), height (control-height/*)
├── border + background по State (Default/Focused/Editing/Error/Disabled/ReadOnly)
├── Leading slot   (иконка / префикс — опц.)
├── Content slot   (сюда каждый компонент кладёт своё: текст+каретка / значение+шеврон / …)
├── Trailing slot  (иконка очистки / шеврон / suffix — опц.)
├── Label          (опц., для Stacked)
└── Supporting Text (опц.)
```

Правка chrome делается **один раз** в `Field` и распространяется на все поля.

### 3.2 Отдельные публичные компоненты — композируют `Field`

Разные, потому что различаются **поведение, анатомия Content, a11y-роль**:

| Компонент | Content | Trailing | Роль / поведение |
|---|---|---|---|
| **Input** | текст + каретка | — / suffix | `textbox`, клавиатура |
| **Textarea** | multiline + каретка | — | `textbox` multiline, растёт по высоте |
| **Search** | текст + каретка | 🔍 leading + × очистка | `searchbox`, семантика запроса |
| **Select** | значение (без свободного ввода) | ▾ шеврон | открывает меню, `combobox`/`listbox` |
| **Combobox** | текст + фильтрация | ▾ + × | `combobox` с автодополнением |

Почему не одна ось `Type`: каретка есть только у text-полей, шеврон — только у select; свойства и клавиатура несовместимы, матрица вздувается, консюмер видит неприменимые пропы.

### 3.3 Единая state-модель (канон для всех)

Свести все поля к общему набору (там, где применимо):

`Default · Focused · Editing · Filled · Error · Disabled · ReadOnly`

- **Search** — дозавести `Error` (невалидный запрос) и `ReadOnly` (если нужен).
- **Textarea** — дозавести `Editing` (каретка после значения) — или осознанно отклонить, если для multiline не нужно.
- **Select** — Editing неприменимо (нет свободного ввода) → у него набор без Editing, зато с `Open` (меню раскрыто).

### 3.4 Единый нейминг

`Leading Icon` / `Trailing Icon` (не `Left/Right`) — во всех компонентах и в `Field`.

---

## 4. Что это даёт

- Консистентность **структурно**, а не дисциплиной ревью.
- Одна правка chrome → все поля (конец ручному копированию, как с кареткой в Search).
- Чистые API у каждого компонента.
- Готовая площадка для **Select / Combobox** — не собираем обвязку заново.

---

## 4а. Решения (2026-07-21)

- **Доставка — через отдельную страницу «Release Candidate»**, а не in-place рефактор. Новый набор (`Field` + Input/Search/Textarea/Select на нём) собирается на RC-странице; опубликованные компоненты и прод-инстансы **не трогаем** до отдельной миграции. Ноль риска сейчас.
- **Select — после `Field`** (Field-first): не плодим ещё одну копию chrome.
- **Гейт: согласование с разработкой ПЕРЕД сборкой.** Неизвестна текущая стадия dev (не собрали ли уже часть, нет ли конфликтов). Сборка RC стартует только после ответа dev. Согласование вынесено на DS-страницу Confluence.

## 5. Фазировка (предложение)

| Фаза | Что | Риск |
|---|---|---|
| **0. Согласование** | Утвердить: единый state-набор, нейминг, состав семейства | — |
| **1. `Field` primitive** | Собрать `.=Field` из общего chrome Input/Search; выверить токены | средний (аккуратно, чтобы не сломать инстансы) |
| **2. Рефактор Input / Search / Textarea** | Перевести на композицию `Field`; выровнять state-модель + нейминг | высокий (много инстансов в проде — нужен план миграции) |
| **3. Новый Select** | Собрать на `Field` (значение + шеврон + меню) | средний |
| **4. Combobox** (по потребности) | text + меню на `Field` | средний |

**Важно:** фаза 2 трогает опубликованные компоненты с инстансами в продуктовых файлах — нужен план миграции (не ломать существующие). Возможен вариант «Field вводим, новые компоненты (Select) сразу на нём, старые мигрируем постепенно».

## 6. Открытые вопросы (нужно решение)

1. **Единый state-набор** — принимаем `Default/Focused/Editing/Filled/Error/Disabled/ReadOnly` как канон? Дозаводим недостающие в Search (Error/ReadOnly) и Textarea (Editing)?
2. **Select сейчас или после `Field`?** Можно собрать Select быстро (скопировать chrome, как раньше) — но это добавит ещё одну копию к дрейфу. Правильнее — сначала `Field`, потом Select на нём.
3. **Масштаб рефактора:** переводить существующие Input/Search/Textarea на `Field` (большая миграция инстансов) — или заморозить их as-is и вводить `Field` только для новых компонентов?
4. **Нейминг:** переименовываем `Left/Right Icon` → `Leading/Trailing Icon` (ломает override'ы инстансов) — делаем или оставляем?
